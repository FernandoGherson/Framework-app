# Framework Deck

A phone-installable flashcard app for the problems that keep coming back. One **deck per problem**
("Can't start a task", "How to influence my manager"), one **card per framework** inside it.
Study a deck in order, or pull a random card when you just need a nudge.

No accounts, no server, no tracking. Everything you write is stored on the device itself.
The web app needs no build step; the Android build is one npm command.

## What it does

| Feature | Detail |
| --- | --- |
| Decks | Create, rename, add a note, delete. Each deck is one problem. |
| Cards | Front = the framework's name, back = how to run it. Add, edit, delete. |
| Study in order | Walks the deck 1 → n, then loops. |
| Random | `Random` button jumps to a random card; the `Random` order mode shuffles the whole deck and reshuffles after each pass. |
| Flip | Tap the card (or Space / Enter) to see the back. |
| Gestures | Swipe left/right on the card for next/previous. Arrow keys and `R` work on desktop. |
| Offline | Service worker caches the app; it runs with no signal. |
| Backup | Menu → Export writes a `.json` file; Import merges one back in. |
| Starter content | Three decks are seeded on first run (also re-addable from the menu). |

## Two ways to run it

| | Web app (PWA) | Android app (APK) |
| --- | --- | --- |
| Install from | The published URL | A `.apk` on the Releases page |
| Updates | Automatic on every push to `main` | Install the new APK over the old one |
| Needs the website | Yes | No, the files ship inside the APK |
| Play Store ready | No | Yes, the same build produces an `.aab` |

Both run the identical code from this repo. They keep **separate** copies of your cards, because the browser and the app are different storage origins. Use Export/Import to move decks between them.

## Install it on your phone (web app)

The app installs as a PWA, which browsers only allow over HTTPS (or `localhost`).

**Easiest route: GitHub Pages**

1. Merge this branch into `main`.
2. Repo → Settings → Pages → Source: **GitHub Actions**. The included workflow
   (`.github/workflows/pages.yml`) publishes on every push to `main`.
3. Open the published URL on your phone.
   - **Android / Chrome:** menu ⋮ → *Add to Home screen* / *Install app*.
   - **iPhone / Safari:** Share → *Add to Home Screen*. (Safari only offers this from Safari itself.)

It then launches full-screen from the home icon, works offline, and keeps its data between launches.

**Local check on a computer**

```bash
python3 -m http.server 8080      # from the repo root
# then open http://localhost:8080
```

Serving it over plain `http://192.168.x.x` to your phone will *run* fine but won't offer the install
prompt, because it isn't a secure context.

## Android app

The Android wrapper is [Capacitor](https://capacitorjs.com/): the same HTML/CSS/JS, bundled into a native shell. `www/` is generated by `npm run build` and is what gets packaged, so the web app and the Android app can never drift apart.

### Getting the APK

The `Build Android app` workflow produces a signed APK and an AAB, and attaches both to a GitHub Release. Run it from Actions → **Build Android app** → Run workflow, or push a `v*` tag for a numbered release. Then open the release on your phone and tap the `.apk`.

It needs one repository secret:

| Secret | What it is |
| --- | --- |
| `KEYSTORE_PASSPHRASE` | Decrypts `android/keystore/release.jks.enc` and unlocks the signing key |

Without it the workflow builds but produces nothing installable, on purpose.

### Why the signing key matters

Android identifies an app by its package name **and** its signature. Every build here is signed with the same key, so a new version installs over the old one and the decks stay. A build signed with a different key cannot install over it; Android forces an uninstall first, which erases everything stored in the app.

So: keep `release.jks` and its passphrase. Losing them means every future update wipes user data.

The encrypted keystore lives in the repo (`android/keystore/release.jks.enc`). The decrypted `.jks` is gitignored and must never be committed.

### Backups

The app's Export writes a JSON file. In the browser it downloads; in the Android app it goes through the system share sheet, so you can drop it into Drive, Keep, or email. Import merges a file back in. This is the only copy of your decks that survives a phone reset.

### Publishing to Google Play later

The workflow already builds `FrameworkDeck-x.y.z.aab`, which is the format Play requires. What's still needed: a Play Console account ($25 one-time), a store listing, a privacy policy URL, and the data-safety form. Since the app collects nothing and talks to no server, that form is short. Play will re-sign the app with its own key (Play App Signing); the key here becomes the upload key.

## Files

```
index.html              screens and sheets
styles.css              mobile-first, follows the system light/dark setting
app.js                  state, storage, study logic
sw.js                   offline cache for the web app (bump CACHE after editing the shell)
manifest.webmanifest    name, icons, standalone display
icons/                  192 and 512 px PNGs
scripts/build-www.mjs   copies the web files into www/ for packaging
capacitor.config.json   app id and name for the Android build
android/                generated Capacitor project, committed so CI can build it
android/keystore/       encrypted release signing key
.github/workflows/      pages.yml publishes the web app, android.yml builds the APK
```

The service worker is skipped inside the Android app: its cache would outlive an app update and keep serving the previous version's files.

## Data and backups

Cards live in `localStorage` under `frameworkDeck.v1`, per device and per app. Clearing site data,
deleting the app, or installing a build signed with a different key deletes them. Use **Export** now
and then; the JSON imports into any other device or into the Android app.
